A Company in a Box: physics, a server sandbox, and a two-tier agent team盒子里的公司：物理世界、服务器沙盒与两层 agent 团队

2026-04-15agentsmulti-agentevaluationsimulation

The problem问题

Running a business requires decisions whose effects persist. A code release changes what customers experience, spending reduces the budget for later decisions, and the environment continues to change between agent calls. I built this sandbox to study whether an LLM team can keep a small ride-hailing platform operating under those conditions. It combines a street-level simulation, software that agents can break and repair, and an organisation with separate permissions for management, architecture and coding. The team has to pay its operating costs and respond to changing demand, failures and competition.

经营公司的决策会持续影响后面的工作：发布的代码决定用户接下来遇到什么，花掉的预算会减少后续选择，而环境在 agent 两次调用之间仍然变化。我搭建这个沙盒，是想观察一支 LLM 团队能否在这些条件下维持小型网约车平台的运营。沙盒包含街道仿真、可以实际修改和修复的软件，以及管理、架构、编码三个权限不同的角色。团队需要支付运营成本，并应对需求变化、故障和竞争。

Design choices设计思路

The diagram shows the sandbox modules as rectangles, the data passed between them as ellipses, and the three roles in different colours. From left to right are the experiment configuration and simulated world, the runner that controls time and accounting, and the agent team with its permitted software targets. The design imposes the following constraints:

图中矩形表示模块，椭圆表示模块间传递的数据，颜色区分三个角色。从左到右分别是实验配置与仿真世界、管理时钟和账本的运行器，以及 agent 团队和各角色可以修改的软件。设计中主要考虑了以下约束：

  • Physics first.物理层在最底下。 Drivers, riders, weather and road closures are simulated on a real street network. Demand, travel times and blocked zones are computed from the state of that simulation.在真实街道网络上模拟司机、乘客、天气和封路，并根据仿真状态计算需求、行程时间和不可通行区域。
  • One ledger, no bailouts.一本账，没有救助。 Server capacity, bandwidth, penalties for unserved orders and agent token usage draw on one balance. The run ends when that balance reaches zero.服务器档位、带宽、未服务订单罚金和 agent 的 token 消耗，都从同一账户扣除。余额归零时运行结束。
  • A server sandbox with a real deploy pipeline.带真实发布流程的服务器沙盒。 Code is changed in a development workspace. An explicit promote operation releases it to production and saves a rollback snapshot. The next simulation tick runs the production version.代码先在开发工作区修改，通过明确的 promote 操作发布到生产环境，并保存回滚快照。下一个仿真步运行生产版本。
  • A two-tier team with locked permissions.权限锁死的两层团队。 Management controls infrastructure spending and submits requests in natural language. Architecture plans the work and alone can release it. The code agent runs once per request and can use a shell only within its workspace.管理层调整基础设施开支，用自然语言提出需求；架构层制定计划，并独自拥有发布权限；代码 agent 每次被调用后完成一项工作，只能在自己的工作区运行 shell。
  • Event-driven wake-ups instead of turn-taking.事件触发的唤醒，而不是轮流发言。 A drop in balance, a spike in unserved orders, a server incident or a new request can wake an agent. A minimum interval between calls limits both response frequency and cost.余额下跌、未服务订单激增、服务器故障或新需求可以触发 agent 调用。两次调用之间设有最小间隔，以限制响应频率和成本。
  • Replayable environments.可重放的环境。 Regime changes, failures and competitor actions are sampled once and saved for replay, so different teams can be tested against the same conditions.市场变化、故障和竞争对手动作先采样并保存，再用于回放，使不同团队面对相同的实验条件。
  • Four-layer replay.四层回放。 Physical, software and management views share a timeline, making it possible to trace a decision through code changes, street activity and the balance.物理层、软件层和管理层视图使用同一时间轴，可以沿着决策追踪代码改动、街道活动和余额变化。

What if we have an agent team to run a company?如果让一支 agent 团队来经营一家公司？

Models can often fix a dispatch bug. I am more interested in what happens when several of them share responsibility for an operating company. How much should each role know, what should it be allowed to change, and how often should it act? Many of the failures I found in this sandbox involved coordination: management sent new requests after every dip in the balance, architecture released changes before receiving feedback on the previous release, and roles with different information had to explain their needs through text.

模型通常能修好一个派单 bug。我更想知道，多个模型共同负责一家持续运营的公司时，会发生什么：各角色应该知道多少、能改什么、多久行动一次？这个沙盒中的许多失败发生在协作环节。例如，管理层在余额每次下跌后都提出新需求；架构层尚未收到上次发布的效果反馈，就再次发布；各角色掌握的信息不同，只能通过文字说明彼此需要什么。

In the runs so far, decision timing and release discipline mattered even when the team could write the required code. Tools that encouraged slower, more considered action often helped. I do not yet know how much of that improvement came from better reasoning and how much from simply intervening less. The sandbox lets me vary role definitions, permissions and wake-up rules to investigate that distinction.

从目前的运行来看，即使团队能写出所需代码，决策时机和发布节奏仍会影响结果。一些让行动更慢、更审慎的工具带来了改善，但还需要区分：究竟是推理质量提高了，还是干预次数减少了？我希望用这个沙盒调整角色分工、权限和唤醒规则，继续检验这些问题。

1Three roles, one clock三个角色，一个时钟

Permissions define what each role can read and change. The tick loop defines when it acts: the runner advances the world, checks triggers, calls the relevant agents and records their costs. The lane diagram follows a feature request from management to architecture, through one code-agent call, and back to architecture for release.

权限决定各角色能读取和修改什么；tick 循环决定何时行动。每一步中，运行器推进仿真、检查触发条件、调用相应 agent，并计入成本。下面的泳道图展示一项需求如何由管理层提出，经架构层规划、代码 agent 实现，再回到架构层发布。

Fixed rules固定规则

  1. Management requests must use natural language. The tool rejects code blocks, function signatures and file names.管理层只能用自然语言提出需求。工具会拒绝代码块、函数签名和文件名。
  2. All costs, including agent tokens, are deducted from the initial balance. No further funds are added.所有成本，包括 agent 的 token 费用，均从初始余额扣除，运行期间不追加资金。
  3. Management can request software changes but has no code access.管理层可以提出软件改动需求，但无权访问代码。
  4. Architecture writes plans and PR briefs; code implementation belongs to the code agent.架构层负责编写计划与 PR 简报，代码由代码 agent 实现。
  5. Architecture can reject a feature request once and must act on the second submission.架构层可以拒绝一项需求一次，再次提交时必须执行。
  6. Only architecture can promote development code to production.只有架构层可以将开发代码发布到生产环境。

3Who sees what, and what to look for谁能看到什么，以及该看什么

Each role has a deliberately limited view. These restrictions let us study coordination under unequal access to information.

各角色掌握的信息受到有意限制，以便研究信息不对称下的协作。

  • Management sees PR summaries and its KPIs, but cannot inspect code, the workspace or the production version.管理层可以查看 PR 摘要与自身 KPI，不能查看代码、工作区或生产版本。
  • Architecture sees requests, the system graph and code, but no ledger or KPIs. Code visibility is another design choice that can be tested.架构层可以查看需求、系统图和代码，无法查看账本与 KPI。是否开放代码视野，也可以作为实验变量。
  • The code agent works inside its workspace without run history, an environment brief or memory from earlier PRs. It exits after each call.代码 agent 在工作区内执行任务，无法读取运行历史、环境简报或此前 PR 的记忆，每次调用后退出。
  • Management communicates with architecture through feature requests and has no direct channel to the code agent.管理层通过需求通道联系架构层，与代码 agent 没有直接通信通道。

What to look for when reading a run读一次运行时该看什么

  • Stale beliefs.过时的信念。 After a regime change, compare management's written hypotheses with the environment's causal structure. Does it still reason from conditions that no longer hold?市场变化后，对照管理 agent 记录的假设与环境的实际因果结构，检查它是否仍在依据已经失效的条件做决策。
  • Damage after a promote.发布之后的损伤。 Track served orders and the balance slope after each release. So far, release timing has been the strongest single signal in the runs.跟踪每次发布之后的订单服务量和余额变化率。在目前的运行中，发布节奏是最强的单一信号。
  • Lever usage.杠杆的使用。 Compare how often management changes infrastructure or submits requests with subsequent profit. Frequent intervention may reflect repeated reactions to losses.比较管理层调整基础设施、提出需求的频率与后续盈利，检查频繁干预是否只是对亏损的反复反应。
  • The token tax.token 税。 Account for the cost of agent calls. When a tool helps, separate the effect of fewer or slower interventions from the effect of better decisions.把 agent 调用费用纳入分析。工具带来改善时，需要区分干预变少、变慢的效果，与决策质量提高的效果。

I use this sandbox to examine team design rather than to produce a leaderboard score. It gives me a way to test how role boundaries, permissions and decision timing affect an agent-run business over time.

我用这个沙盒研究团队设计，观察角色边界、权限和决策节奏怎样影响一家由 agent 经营的公司，以及这些影响如何随时间积累。
