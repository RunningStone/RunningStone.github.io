这次实验让我看到了什么

有一段时间，我只需要说出想做的事，agent 就会替我调用软件、整理信息、安排任务。生活确实清静了不少。可随着服务和 skill 越装越多，我又开始忙着排查故障、修配置、管权限。系统省下的注意力，逐渐花回了维护上。

这些问题涉及整个软件栈，单靠换一个更强的模型很难解决。后来看到 DeepSeek Harness，我觉得 harness 层终于有了值得继续尝试的方向；其他部分，还需要逐项接起来。

  • 我一直在补什么 回头看，许多维护工作都在补系统缺少的功能：建频道是替 agent 划分记忆，排 cron 是替它安排任务，查资源和重启是在做运维，修 skill 是在维护集成。注册小号、另起看护者，也都是为了让这套系统能放心地长期开着。
  • 软件和机器怎么管 我需要一个有足够资源和优先级的 Owner Agent，在故障时负责恢复；还需要运行时向它说明，哪些容器提供哪些能力、彼此怎样依赖、占用多少资源。应用中可复用的功能应能单独接入，生活数据也应统一管理。这次整理的项目能解决其中一些问题，还没能提供这套完整的系统状态。
  • 对话和结果怎么组织 我希望随时开口，agent 就能找回这件事需要的背景，不必先由我选频道。结果也应该按任务呈现：健身计划适合表格，统计结果适合图表。记忆库和 UI 协议已经提供了不少工具，如何把它们接进日常消息入口，仍需要自己处理。
  • 怎样替我在网上办事 替我读信息和替我采取行动，需要不同的权限。我想要的是绑定主账号的 agent 账号、操作前的轻量确认，以及稳定且获授权的信息接口。密钥代理、身份委托和审批都有相关项目，但把这些接到具体平台上，仍有很多工作要做。
  • 全天在线的成本 简单任务尽量交给本地模型，复杂规划再调用能力更强的云端模型，并按任务控制预算。除了选择模型，我还希望任务能带着已有进展在模型之间交接。本次整理找到了预算和路由工具，尚未找到满足这一交接需求的完整方案。
  • 为什么关注 DSH DeepSeek Harness 让我看到了改善插件维护的可能：组件可以替换，依赖由运行时管理，执行过程也能追溯。这与我修 skill、处理升级故障时遇到的问题紧密相关。不过，可回滚的插件并不能直接保证 skill 跨模型表现一致；机器资源、生活数据和外部服务的接入，也还要另行解决。

五个阶段

① 新鲜期 安装 · 备灾 · 账号 · 初步收获

这段经历

最开始用 OpenClaw 时，我的体验很一般，一时没明白它为什么会火。用了一阵才发现，把对话放进日常消息软件，确实方便了很多。更让我感兴趣的是，那些过去嫌安装麻烦的开源软件，现在可以让 agent 帮忙部署和配置。它像一块能黏在各种软件上的橡皮泥，把我的需求和软件接了起来。

Mac mini 上很快装了十几个自托管服务，也跑起了本地 Ollama 和网关。麻烦随之而来：安装时的 token 消耗很高，机器卡死后 agent 也起不来，我还得想办法避免直接把主账号交给它。

用起来怎样

虽然安装不顺，能用起来的部分还是让我兴奋。每日新闻、论文整理和讲解、健身建议、用餐热量估算，这些过去要到处找 App 才能凑齐的功能，开始出现在同一个对话里。

需求拆分

  • 部署层 · 让 agent 部署和配置自托管软件
  • 备灾层 · 主系统故障时，仍能工作的看护者
  • 身份层 · 绑定主账号、权限受限的 agent 账号
  • 计算层 · 按任务分配本地与云端模型，控制运行成本

当时的办法

  • → N1 我告诉 OpenClaw 想用什么，它负责尝试部署和配置。Mac mini 上很快装了十几个自托管服务。
  • → N2 另起一个基于 nanoclaw 的小 agent，只做三件事：重启 OpenClaw、重启本地 Ollama、重启网关。它需要独立于主系统运行，这也让我开始考虑 Owner Agent 的资源和优先级。
  • → N3 为 agent 注册各平台的账号，加为主账号的协作者，再关联到 JumpCloud。我先用这个办法划开权限。
  • → N4 日常用本地 Ollama，遇到难任务再手动切到云端。本地推理会与业务服务争资源，一串长工具调用可能让两边都跑不动。

后来想到的

当时的办法都很直接：部署让 OpenClaw 自己摸索；另起一个基于 nanoclaw 的小 agent，只负责重启 OpenClaw、Ollama 和网关；给 agent 注册各平台的小号，再关联到 JumpCloud；本地模型处理不了的任务，手动切到云端。看护者必须独立运行，否则主系统倒下时，它也帮不上忙。后来我设想 Owner Agent 时，首先想到的就是要给它留出资源和更高的优先级。

相关开源项目

  • N1 直接 自托管 PaaS，提供 REST API 和内置只读 MCP 端点；社区 coolify-mcp 补充写操作。
  • N1 直接 自托管 PaaS，提供 Compose 部署和模板目录；官方 MCP 包含 67 个工具。
  • N2 部分 自托管监控，支持多渠道告警；故障修复仍需另行处理。
  • N2 部分 通过定期心跳检测运行状态；agent 未按时上报时发出告警。
  • N3 直接 Rust 凭证网关：agent 使用占位 key，由网关代入真实密钥，并提供策略和审批控制。
  • N3 直接 管理 agent 身份，支持 RFC 8693 token exchange 委托链、限时凭证、实时撤销和人工审核。
  • N4 直接 统一接入 100+ 模型提供商及 Ollama，支持虚拟 key、项目预算和故障回退路由。
  • N4 直接 根据任务难度、成本和隐私要求，将请求路由到本地或前沿模型。

② Skill 膨胀期 自动化增多 · 维护吃力 · 上下文混杂

这段经历

接下来，我装了很多 skill，也自己写 skill 和少量适配代码。许多事情交代一次就能反复执行，起初很省心。

数量一多，维护却跟不上了：命名越来越乱，换模型后有些 skill 就不再好用，出了问题还得我逐个修改。我开始想，能不能把这些工作交给已有的开源软件？与此同时，编写和使用 skill 的 token 开销不断增加，记忆库里的内容混进上下文后，agent 也更容易答非所问、忘记刚确认的事。

用起来怎样

刚开始是“终于不用再重复交代了”，后来却常常在修自己写的 skill。自动化省下了一些重复操作，也带来了一批需要长期维护的东西。

需求拆分

  • Skill 治理 · 把 skill 的命名、版本和加载方式管起来
  • 抽象边界 · 换模型时，工具仍能按约定工作
  • Skill 自进化 · 根据失败记录修复 skill，并验证修改
  • 记忆层 · 根据当前话题，找回需要的记忆
  • 上下文预算 · 控制上下文长度，也看清 token 花在哪里

当时的办法

  • → N5、N6、N7 自己写了很多 skill 和少量适配代码。模型一换，有些 skill 就失效；特殊情况越补越多，最终都得逐个维护。
  • → N8 健康、工作、项目和生活分开聊，方便自己查找，也帮助 agent 判断背景。但每次先想“该在哪个频道说”，仍然会打断思路。
  • → N9 Agent 开始答非所问或频繁忘事时，我就手动压缩对话，或者另开一个会话。

后来想到的

这时，一个能力通常由三部分组成：skill、薄适配层和软件后端。后端往往很稳定，skill 和适配层却容易出问题；有时只是换了模型，skill 就得重写。我需要更清楚的工具契约和兼容性验证。记忆也不能全靠会话承载：对话会被压缩、截断和切换，未经证实的猜测还可能和已确认的事实混在一起，需要另行记录和区分。

相关开源项目

  • N5 直接 SKILL.md 开放标准，通过 name、description 描述 skill，正文按需加载；资料记录约 40 个 agent 产品采用。
  • N5 直接 面向 75+ agent 的 skill 包管理器，提供安装、版本锁定和更新。
  • N5 直接 OpenClaw 官方 skill 注册表，提供语义化版本、更新记录、向量搜索和安全扫描。
  • N6 直接 为工具、资源和提示提供不依赖特定模型的接口约定。
  • N6 直接 官方 MCP 客户端与服务端一致性测试框架，资料记录于 2026-07 起提供。
  • N7 直接 复杂任务完成后可创建 skill，并在使用中改进；这些能力依附于自身的 harness。
  • N7 直接 arXiv:2604.01687（COLM 2026）对应的研究代码，围绕 skill 包生成、隔离验证和失败反馈进行迭代。
  • N8 直接 用时序知识图谱记录事实变化，并保留 episode 级来源。
  • N8 直接 沿用 MemGPT 的分层记忆思路，提供有状态的 agent 平台。
  • N8 直接 结合向量、图和键值存储，自动抽取信息，可作为记忆层接入。
  • N9 直接 提供 LLM 运行观测和评估，可按执行记录查看 token 用量。
  • N9 直接 先提供精简工具描述，选中后再加载完整 schema；资料记录的 token 节省幅度为 70–97%。

③ 自托管期 四层结构 · 唯一入口 · 容器挤占资源

这段经历

后来，我把系统整理成 harness → skill → 薄适配代码 → 开源自托管服务四层。食谱、冰箱库存、健身和每月花销等数据交给十几个专业服务保存，比放在 skill 和 Markdown 里清楚得多，也有面板可以核对。

这一阶段的后半段，我真的做到了只和 agent 对话：不再主动打开网站、App、邮件、频道或后台。邮件由它阅读和起草，我只确认或稍作修改。每天面对的，只剩一个简单的文字聊天窗口。

但对话一长，它就容易跟丢话题，我只好按健康、工作、项目和生活建频道；健身计划等结果又常常是一大段文字。后台也越来越重：每个应用都带着数据库、前后端、代理、缓存或 worker，几十个容器把 Mac mini 挤到卡死，负责修复的 agent 也无法启动。

用起来怎样

只用一个入口的那段时间，生活突然变得很干净。我不用在几十个 App、网页和通知之间来回跳，注意力消耗明显少了。不过，每次开口前先想“这句话该在哪个频道说”，仍然费心；面对一长段健身计划时，又觉得自己像从图形界面退回了终端。后来机器频繁卡死，维护就成了更大的负担。

需求拆分

  • 专业软件层 · 用专业软件记录和管理生活数据
  • 运行时/编排层 · 让 agent 掌握服务依赖、资源和恢复顺序
  • 统一数据层 · 让服务共用一套生活数据
  • 能力拆解层 · 从完整应用中拆出可复用的功能
  • 信息接入层 · 把社区、本地信息和地图接到同一个入口
  • 呈现层 · 根据任务呈现表格、图表和交互卡片
  • 记忆层 · 根据当前话题，找回需要的记忆

当时的办法

  • → N10、N12、N13 按 harness、skill、薄适配代码、开源服务分成四层。专业软件保存数据、提供面板，skill 和适配代码负责接入，记录终于方便核对了。
  • → N11 用 Compose 逐个启动服务，出问题后再让 agent 查资源、关服务、重启、改配置、恢复任务。我得不断参与维护，才能让系统继续运行。
  • → N18 健身计划和统计结果常是一大段文字，我得自己从中找出项目和数值，再在脑子里整理成表格。

后来想到的

这一阶段让我确认，只通过 agent 处理日常事务是可以做到的，也让我更具体地看到了缺什么。机器需要有人管理资源、依赖和恢复顺序；生活数据需要统一组织；对话需要按当前情景找回记忆；输出需要适合任务的界面。

既然 agent 已经替我读邮件，我也自然希望它能继续替我筛选社区、消息和更新，让我只看需要关注的部分，并在必要时回到原始来源。

④ 离开期 维护负担 · 办事受阻 · 权限和升级

这段经历

最后，我因为维护太费心离开了 OpenClaw。日常任务也有不少做不完的地方：问“附近有什么好吃的”，接入信息源要花钱，结果还不如我自己搜小红书；餐厅只接受电话订位，它就办不了；即便订好了，也没能在我确认后接着写进日历。

权限越来越难管，几次不兼容的更新又让 skill 适配层失效。原本用来省心的系统，逐渐成了另一份需要照料的工作。

用起来怎样

我最在意的变化，是自己又开始围着系统转：它本来替我处理琐事，现在我得不断提醒它查故障、修配置、恢复任务。省下的注意力又花了回去。

需求拆分

  • 意图调度 · 说清目标后，让系统安排执行时间
  • 行动层 · 把订位、网页操作和日历回写接起来
  • 信息接入层 · 把社区、本地信息和地图接到同一个入口
  • 审批门 · 需要确认时，给我一个简单的操作入口

当时的办法

  • → N14 我得替 agent 决定每项任务几点执行；遇到调度器或版本问题，还要处理同一天重复运行的情况。
  • → N16、N15 缺少适合 agent 的数据接口时，我让它操作图形界面，并用额外账号减少主账号受到的影响。
  • → N17 删除、支付和发送先由我自己处理。这部分工作也就暂时无法自动化。

后来想到的

这些任务里，模型往往已经理解了我的意思，后续却卡在账号、认证、授权和具体操作接口上。调度也类似：我只是想让它“每天完成一次”，还得自己安排时间、避开其他任务、处理重复执行。经过这一轮折腾，我想要的系统反而更明确了：一个全天在线、能自己安排任务和处理常见故障的 agent，让我少操心，运行成本也尽量低。

相关开源项目

  • N14 部分 持久执行引擎，Schedules 提供时间抖动、重叠策略和补执行窗口，仍需配置具体调度规则。
  • N14 部分 提供 cron 调度、避免重复注册的 deduplicationKey，以及时间窗错峰。
  • N15 部分 实时语音 agent 框架，支持 SIP 电话接入；订位流程仍需自己组织。
  • N15 部分 让 agent 操作网页；涉及登录和支付时，还需接好授权与确认流程。

这段经历

后来我看到了 DeepSeek Harness。它用两句话概括设计：“Everything is a plugin. Every run is traceable.” 模型、工具、skill、会话、沙箱、存储、循环、调度和 UI 都按插件组织，通过配置组合；交互则写入只追加的会话文件，用于回放和创建分支。

它的底层是 Cordis，对应论文《A Programming Paradigm for Spatiotemporal Composability》（Shi、Zhang、Cui，北大与 DeepSeek-AI，arXiv:2608.25512，2026-08-26）。按我的理解，时间可组合性关心的是组件移除后，如何撤销它在上下文中留下的副作用，每次上下文变换都带一个由运行时管理的逆操作；空间可组合性关心的是组件声明依赖后，运行时如何据此激活和停用它。

  1. 进程监督、文件备份、指标、消息持久化和密钥管理已有明确实现。 这些不是必须重新发明的 agent 功能。剩余工作主要是正确配置、接入与验证。
