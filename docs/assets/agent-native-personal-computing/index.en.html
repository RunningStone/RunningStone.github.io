In 2026, Can I Just Talk to an Agent and Stop Opening Other Apps?

2026-08-26 · Project research compiled on 2026-09-08

I built an always-on personal agent system on a Mac mini using OpenClaw and a collection of self-hosted services. This article follows how it took over email, news and personal records, and the system gaps that emerged as I installed it, expanded it and tried to keep it running. I saw a beautiful future, even though I was still stuck in the hell of missing infrastructure. It felt like the dawn of the automobile: people driving something that still looked like a carriage body through the mud, only to break down a kilometre outside town.

Yes—but at the time, only because I was willing to double as the system's operations engineer. I really did have days when I only talked to the agent and stopped opening other apps and websites myself. The backend services had not disappeared; I no longer had to operate them one by one. Then fixing skills, diagnosing failures, managing permissions, handling upgrades and dealing with exhausted resources consumed the attention I had saved. Turning the user into a system administrator does not fulfil the promise of a personal assistant. For LLM companies to make this way of living viable, they must turn the whole system into a consumer product that ordinary people can buy and keep using, taking maintenance off the user's hands. That requires more than stronger models: harnesses need enormous advances in integration, state management, compatibility and failure recovery.

What this experiment showed me

For a while, I only had to say what I wanted to do. The agent would use software, organise information and arrange tasks for me. Life really did become quieter. But as I installed more services and skills, I found myself troubleshooting failures, fixing configuration and managing permissions again. The attention the system had saved was gradually being spent on maintenance.

These problems span the software stack. Simply switching to a stronger model is unlikely to solve them. When I later came across DeepSeek Harness, I felt there was finally a direction worth exploring at the harness layer. The other parts still need to be connected, one by one.

  • What I kept filling in Looking back, much of the maintenance was compensating for missing system functions. Creating channels meant organising memory for the agent; setting up cron meant scheduling its work; checking resources and restarting services meant doing operations; fixing skills meant maintaining integrations. Extra accounts and a separate watchdog were also attempts to make the system safe enough to leave running.
  • Managing software and the machine I need an Owner Agent with enough resources and priority to handle recovery. I also need a runtime that can tell it which capabilities each container provides, how the containers depend on one another and how much resource they use. Reusable application functions should be accessible separately, and everyday data should be managed together. The projects in this survey solve some of these problems, but do not yet provide that complete view of system state.
  • Organising conversations and results I want to start speaking whenever I need to, with the agent retrieving the relevant background instead of making me choose a channel first. Results should suit the task: tables for workout plans, charts for statistics. Memory libraries and UI protocols already provide many useful tools. Connecting them to my everyday messaging interface still takes work.
  • Acting for me online Reading information for me and taking action for me require different permissions. I want an agent account linked to my main account, lightweight confirmation before an action, and stable, authorised information interfaces. There are projects for credential proxying, delegated identity and approval, but connecting them to specific platforms remains a substantial job.
  • The cost of staying online Simple tasks should stay with local models where possible; complex planning can use stronger cloud models, with a budget for each task. Beyond choosing a model, I want tasks to carry their progress when handed from one model to another. This survey found budget and routing tools, but not a complete solution for that handoff.
  • Why DSH caught my attention DeepSeek Harness suggests a way to improve plugin maintenance: components can be replaced, dependencies are managed by the runtime, and execution can be traced. That is closely related to the problems I encountered fixing skills and handling upgrades. Still, reversible plugins do not directly guarantee consistent skill behaviour across models. Machine resources, everyday data and external services also need separate integration.

Five stages

① The novelty phase Installation · Recovery · Accounts · Early benefits

What happened

My first experience with OpenClaw was unremarkable. I did not immediately understand why it was so popular. After using it for a while, I realised that putting the conversation inside an everyday messaging app did make things much easier. What interested me more was that the agent could help deploy and configure open-source software I had previously avoided because installation was a hassle. It was like a piece of modelling clay that could stick to different programs, connecting what I wanted with the software that could do it.

Before long, the Mac mini had more than a dozen self-hosted services, local Ollama and a gateway running on it. Problems followed: installation consumed a lot of tokens; when the machine froze, the agent could not start either; and I had to find a way to avoid handing it my main accounts outright.

What it was like to use

Even with the installation trouble, the parts that worked were exciting. Daily news, collecting and explaining papers, fitness advice and estimating meal calories had previously required a collection of apps. Now they were beginning to appear in one conversation.

The needs behind it

  • Deployment · Let the agent deploy and configure self-hosted software
  • Recovery · A watchdog that still works when the main system fails
  • Identity · A restricted agent account linked to my main account
  • Compute · Allocate local and cloud models by task, within a running budget

What I tried

  • → N1 I told OpenClaw what I wanted to use and let it try deployment and configuration. More than a dozen self-hosted services soon appeared on the Mac mini.
  • → N2 I ran a small, separate nanoclaw-based agent with just three jobs: restart OpenClaw, restart local Ollama and restart the gateway. It had to work independently of the main system, which also made me think about resources and priority for an Owner Agent.
  • → N3 I registered platform accounts for the agent, added them as collaborators to my main accounts, then linked them to JumpCloud. That was my first way of separating permissions.
  • → N4 I used local Ollama day to day and switched manually to the cloud for difficult tasks. Local inference competed with application services; a long sequence of tool calls could leave both unable to make progress.

What I came to think

My workarounds were straightforward: let OpenClaw figure out deployment; run a small, separate nanoclaw-based agent whose only jobs were to restart OpenClaw, Ollama and the gateway; register secondary accounts for the agent and connect them to JumpCloud; switch manually to a cloud model when the local one could not handle a task. The watchdog had to run independently, or it would be no help when the main system went down. Later, when I began imagining an Owner Agent, the first requirement was to reserve resources and give it higher priority.

② Skill sprawl More automation · Harder maintenance · Mixed-up context

What happened

Next, I installed lots of skills and wrote my own skills with small amounts of adapter code. Many tasks could be explained once and then repeated automatically. At first, that was a relief.

As the collection grew, maintenance fell behind. Names became inconsistent; some skills stopped working well after a model change; and I had to fix failures one by one. I began wondering whether existing open-source software could take over some of this work. Meanwhile, writing and using skills kept consuming more tokens. As material from the memory store entered the context, the agent also became more likely to answer the wrong question or forget something we had just confirmed.

What it was like to use

At first it felt like, finally, I do not have to explain everything again. Later, I was often repairing skills I had written myself. Automation saved some repetitive work, but also created a collection of things that needed ongoing maintenance.

The needs behind it

  • Skill governance · Manage skill names, versions and loading
  • Tool contracts · Keep tools working to contract when the model changes
  • Skill improvement · Repair skills from failure records and verify the changes
  • Memory · Retrieve the memories that fit the current conversation
  • Context budget · Control context length and see where the tokens go

What I tried

  • → N5, N6, N7 I wrote many skills and a small amount of adapter code. Some skills failed after a model change. Patches for special cases accumulated, and I had to maintain each one.
  • → N8 I separated health, work, projects and daily life to make things easier to find and help the agent infer the context. But deciding which channel to speak in still interrupted my train of thought.
  • → N9 When the agent began answering the wrong question or forgetting things repeatedly, I manually compressed the conversation or opened a new session.

What I came to think

At this point, a capability usually had three parts: a skill, a thin adapter and a software backend. The backend was often stable; the skill and adapter were more fragile. Sometimes changing the model was enough to require rewriting the skill. I needed clearer tool contracts and compatibility checks. Memory could not depend entirely on conversations either: they get compressed, truncated and switched, and unverified guesses can mingle with confirmed facts. Those need to be recorded and distinguished separately.

③ The self-hosting phase Four layers · One interface · Containers competing for resources

What happened

I eventually organised the system into four layers: harness → skill → thin adapter code → open-source self-hosted service. More than a dozen specialist services stored recipes, fridge inventory, fitness records and monthly spending. That was much clearer than keeping everything in skills and Markdown, and I had dashboards I could check.

In the latter part of this phase, I really did interact only with the agent. I stopped actively opening websites, apps, email, channels or admin panels. It read and drafted my email; I only confirmed or made small changes. My daily interface was a simple text chat window.

But it easily lost the thread in long conversations, so I created separate channels for health, work, projects and everyday life. Results such as workout plans were also often long blocks of text. The backend grew heavier too: each application brought its own database, frontend, backend, proxy, cache or workers. Dozens of containers eventually overwhelmed the Mac mini, and the agent responsible for repairs could not start either.

What it was like to use

During the period when I used just one interface, life suddenly felt uncluttered. I was no longer jumping between dozens of apps, pages and notifications, and it took noticeably less attention. Still, having to decide which channel to speak in was a burden. Faced with a long workout plan, I also felt as though I had moved from a graphical interface back to a terminal. Later, frequent freezes made maintenance the bigger problem.

The needs behind it

  • Specialist apps · Use specialist software to record and manage everyday data
  • Runtime · Give the agent a view of dependencies, resources and recovery order
  • Shared data · Let services share a common set of everyday data
  • Reusable functions · Extract reusable functions from complete applications
  • Information access · Bring communities, local information and maps into one interface
  • Presentation · Present tables, charts and interactive cards suited to the task
  • Memory · Retrieve the memories that fit the current conversation

What I tried

  • → N10, N12, N13 I separated harness, skill, thin adapter code and open-source service. Specialist software stored data and provided dashboards; skills and adapters connected it. Records finally became easy to check.
  • → N11 I started services one by one with Compose. When something failed, I asked the agent to inspect resources, stop services, restart, change configuration and recover tasks. Keeping the system running required my continual involvement.
  • → N18 Workout plans and statistics often arrived as long blocks of text. I had to pick out the items and values and mentally arrange them into a table.

What I came to think

This phase convinced me that handling everyday tasks through an agent alone was possible. It also made the missing pieces more concrete. Someone had to manage machine resources, dependencies and recovery order. Everyday data needed a common organisation. Conversations needed to retrieve memory for the current situation. Output needed an interface suited to the task.

Since the agent was already reading my email, I naturally wanted it to filter communities, messages and updates too: show me what needed attention, and let me return to the original source when necessary.

④ Walking away Maintenance burden · Unfinished tasks · Permissions and upgrades

What happened

In the end, I left OpenClaw because maintaining it demanded too much attention. Many everyday tasks could not be completed either. When I asked for somewhere good to eat nearby, access to information sources cost money, and the results were worse than searching Xiaohongshu myself. If a restaurant accepted bookings only by phone, the agent could not make one. Even when a booking was made, it did not go on to add it to my calendar after my confirmation.

Permissions became harder to manage, and several incompatible updates broke skill adapters. A system that was supposed to save me trouble gradually became another job to look after.

What it was like to use

The change that mattered most was that I was organising my time around the system again. It had been handling chores for me; now I had to keep reminding it to investigate failures, fix configuration and recover tasks. The attention I had saved was being spent all over again.

The needs behind it

  • Intent scheduling · State the goal and let the system choose when to execute
  • Actions · Connect bookings, browser actions and calendar updates
  • Information access · Bring communities, local information and maps into one interface
  • Approval · Give me a simple interface when confirmation is needed

What I tried

  • → N14 I had to choose each task's execution time for the agent. Scheduler or version problems also meant handling duplicate runs on the same day.
  • → N16, N15 When suitable data interfaces were unavailable, I had the agent use the graphical interface, with extra accounts to reduce the impact on my main accounts.
  • → N17 I continued handling deletions, payments and sends myself. That part of the work therefore remained unautomated.

What I came to think

In these tasks, the model often understood what I meant. The next steps got stuck on accounts, authentication, authorisation or particular action interfaces. Scheduling was similar: I only wanted something done once a day, but still had to choose a time, avoid other tasks and handle duplicate runs. After all that tinkering, what I wanted was clearer: an always-on agent that could schedule its own work and handle common failures, letting me worry less while keeping running costs as low as possible.

⑤ Discovering DSH Composable plugins · Traceable runs

What happened

Later, I came across DeepSeek Harness. It describes its design in two sentences: “Everything is a plugin. Every run is traceable.” Models, tools, skills, sessions, sandboxes, storage, loops, scheduling and UI are organised as plugins and composed through configuration. Interactions go into append-only session files for replay and branching.

Underneath is Cordis, described in A Programming Paradigm for Spatiotemporal Composability (Shi, Zhang and Cui, Peking University and DeepSeek-AI, arXiv:2608.25512, 2026-08-26). As I understand it, temporal composability concerns undoing the side effects a component leaves in its context when removed: each context transformation has an inverse managed by the runtime. Spatial composability concerns how the runtime activates and deactivates components according to their declared dependencies.

What it was like to use

That renewed my interest. Component dependencies and upgrades, which I had been managing by hand, now had explicit mechanisms and a formal description. I could keep asking how far those mechanisms would actually take me.

The needs behind it

  • Harness · Organise the system as plugins and keep a record of every run

What I tried

  • At this stage, I began exploring how existing projects approached these problems.

What I came to think

I see it as a milestone at the harness layer. Reversible components help with replacement and upgrades; dependency management addresses some of the maintenance burden from accumulating skills; run records provide evidence for investigating failures and improving skills. These are related to N5, N6 and N7, but still need testing on concrete tasks.

OpenClaw let me experience a life with only an agent as my interface. DSH suggested a way to keep improving that system. Resource management, data integration, identity, authorisation and access to everyday services still need work.

Related open-source projects

  • N19 direct Plugins for models, tools, skills, sessions, sandboxes, storage, loops, scheduling and UI; append-only session logs underpin run records, with dsh-user-approval unifying ask/never policy.
  • N19 direct The meta-framework beneath DSH (arXiv:2608.25512), providing reversible side effects, reactive dependency management and hot reloading.
  • N19 partial Extensible through MCP servers, with replaceable models; the recorded version does not offer equivalent replacement of sessions, sandboxes and scheduling.

1. How to read this survey

Start with capabilities, find implementations, then assess the gaps. Do not work backwards from project names to a shopping list of software to install. The tables contain 49 candidate implementations, including SQLite's public-domain code, alongside native OS mechanisms and one source-available project excluded from the open-source candidates.

  • Direct (sub-capability): official documentation describes an interface or mechanism explicitly matching that sub-capability. This does not mean the whole B or S requirement is met.
  • Integration: existing components need to be connected through configuration or custom code.
  • Partial: only part of the requirement is covered, or the platform or trust assumptions differ from the target.

2. The main findings

  1. Process supervision, file backup, metrics, persistent messaging and secret management have clear existing implementations. These do not need to be reinvented as agent-specific features. Most remaining work is configuration, integration and verification.
  2. Task semantics still require substantial integration. “Protect important tasks”, “complete this once a day” and “add a calendar event after booking” cross scheduling, resources, permissions and external side effects. A component's retry support does not solve the whole problem.
  3. Recovery means three different things. Restarting a process, restoring data and resuming the business task have different acceptance criteria. restic, pgBackRest and Temporal each address part of that work.
  4. The Mac host and Linux service environment must be distinguished. systemd/cgroup and gVisor/Firecracker constraints cannot be applied to native macOS processes. Lima supplies a Linux environment; it does not remove the host's resource limits.
  5. Security tools cover different stages. Threat Dragon models threats, Trivy scans, Cosign verifies signatures, OPA evaluates policy and sandboxes restrict execution. None alone proves an agent safe.
  6. Community code and commercial products sharing its name must be separated. LiteLLM, Mem0 and FastMCP have explicit notes on this boundary. The immudb main branch reviewed uses the Business Source License; see the exclusion below.

These are findings about capabilities and sources, not new claims about what I have or have not deployed.

8. Four combinations worth testing next

5. Conventions for the second diagram and project research

The second diagram is organised by knowledge area and testable capability, linked to personal experience, system mechanisms, open-source projects and remaining gaps. N retains its historical provenance. B/S are check indices; unrecorded items are not forced into a historical stage.

Projects must have checkable functional evidence and licences. Every claim of coverage applies to an explicit sub-capability, with its platform, integration work and exclusions stated. This round checks documentation and source-code declarations; it does not imply installation, load testing, security auditing or recovery drills.

Four cross-cutting groups take priority: an independent minimum recovery mechanism; file and database restoration; events and durable tasks; and identity, execution boundaries and action audits. See the full capability and open-source implementation survey.

6. Decisions in this revision

Knowledge areas and operations replace the attempt to arrange every concept in one stack. Original identifiers remain for comparison. A capability may span OS, data and security, so repeated edges must not be counted as independent gaps.

Statements such as “none”, “never” and “zero” were replaced with evidence states supported by the available material; causal claims became questions to verify. This takes more words, but avoids turning a classification checklist into invented experience.
