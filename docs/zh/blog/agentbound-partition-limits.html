任务切分和通信瓶颈带来的极限

2026 年 9 月 8 日 · agentsmulti-agentinformation-theorypaper

论文：How Task Structure Limits Multi-Agent Success: An Information-Theoretic Analysis，与 Ming Luo 合作。这篇是通俗版。图、表和公式都直接取自论文；倒数第二节关于多轮 agent 的解读是我自己的，比定理字面上说的多走了一步。

一个三个人修不好的 bug

想象一个 bug，修它要动三处：一个 parser，一个 validator，还有同时覆盖两者的测试。parser 吐出什么，validator 就得接受什么，测试又把两边都钉死。现在把三个文件交给三个互相看不到 diff 的工程师。每个人都会交出一份完全合理的补丁，合起来却跑不过，因为让这个任务难的东西从来不在任何一个文件里，它在文件之间的边上。

多智能体系统（MAS）的卖点是绕过单 agent 的极限：把任务拆开，一人一块，最后合并。可实证结果很尴尬：在复杂 benchmark 上，MAS 经常输给用同一个模型的单 agent。常见的解释都是工程层面的：协调开销、错误传播、角色冗余。我们的观点是，工程问题下面还有一个任务本身的性质，它给出了一个任何架构都抬不动的天花板。

每个任务都有一个核

把任务写成约束图：节点是你要做的决定，边连接两个互相牵制的决定，每条边带一个熵 $H(\phi_e)$，表示这条约束里有多少信息。大多数真实任务都有一层容易拆的外壳，和一个每个决定都依赖好几个别的决定的硬核。论文把这个区域叫不可约瓶颈 $\tau_{\text{hard}}$，我就叫它"核"。

把核分给 $m$ 个 agent。任何分法都会切断一些边。最省的那种分法的代价是

$$C_{\min} := \min_{\mathcal{P}} \sum_{e \in E_{\mathrm{cut}}(\mathcal{P})} H(\phi_e)$$

整个想法就在这一行里。$C_{\min}$ 是不管你分得多聪明都必须切断的约束比特数。它是任务的属性，不是框架的属性。

它能有多大？论文在六种教科书图族上把闭式公式和暴力最小割对了一遍。链只需切一条边；八个节点的完全图怎么切都要断十六条。这就是流水线型任务（拆得干净）和"什么都牵制什么"型任务（拆不干净）之间的差距。

切核的代价是指数级的

被切断的边是没有任何人完整持有的约束。第一个结果说，系统关于正确解 $\tau^\star$ 缺失的信息至少和切割成正比：

$$H(\tau^\star \mid \mathrm{Internal}) \ \ge\ c_1 \cdot C_{\min}$$

其中 Internal 是 agent 一开始拿到的全部东西。这个缺口在任何 agent 跑起来之前就已经被任务定死了。

缺的比特会变成失败概率。要成功就得把没有的比特猜出来，而猜对 $k$ 个比特的概率大约是 $2^{-k}$。定理 1 把这件事写精确：

$$P(\text{success}) = O\!\left(2^{-\Omega(C_{\min} - H_{\mathrm{sol}})}\right)$$

$H_{\mathrm{sol}}$ 是给"可接受答案很多"的任务打的折扣。答案唯一时它是零，成功率就只随切割指数衰减。

在受控条件下这个关系是精确的。三色图着色的测试床里，每切一条边理论上应该丢掉 $\log_2(3/2) \approx 0.585$ 比特，实测的信息缺口正好是这个数：

这个上界需要几条"典型性"条件：被切的约束不能和 agent 手里已有的东西暗中冗余，解空间里不能有让你猜得远好于熵预测的捷径。这些条件就是"这真的是核"的形式化版本。如果一个任务违反它们，说明它还能重构，真正的核比看上去小。

封闭系统里，多聊没用

最直接的补救是让 agent 之间多交流。下面是我觉得最反直觉的结果。在封闭系统里（运行过程中不接触外部世界），无论通信多少轮 $T$：

$$I(\tau^\star;\ \mathrm{Internal}, \mathcal{M}^{(1:T)}) = I(\tau^\star;\ \mathrm{Internal})$$

每条消息都是发送者已知信息的函数。通信可以把信息在 agent 之间重新分配，却不能创造出谁都没有的、关于解的信息。所以上一节的上界不会因为加带宽而移动。下图左边是合成实验的验证：一个 $C_{\min}=4$ 的网格，agent 之间交换零比特还是一百比特，成功率都平在三分之一附近。

论文小心地留了两条注脚。这个引理只针对封闭系统，以及消息只依赖本地信息和之前消息的协议。而且它说的是天花板，不是天花板以下的一切：通信当然能帮 agent 更好地用上已有的信息，只是付不了切割那笔账。

反馈是唯一能付账的货币

现在把系统打开。令 $F$ 是 agent 通过在真实世界里执行某个动作换来的反馈比特（一个挂掉的测试、一条编译错误、用户的一句纠正），$R$ 是这些反馈里回传到规划者那里的比特。定理 3：

$$P(\text{success}) \le O\!\left(2^{-\max(0,\ c\,C_{\min} - F - R - H_{\mathrm{sol}})}\right)$$

指数是剩余缺口。反馈比特直接从切割里减掉，当 $F + R$ 达到 $c\,C_{\min} - H_{\mathrm{sol}}$ 时指数归零，成功就不再是指数级小概率。这是一个相变，上图右边在同一个网格上展示了它：零反馈时三分之一，1.6 比特时超过九成，3.2 比特时全部成功，实测临界点和预测的 1.29 比特对得上。

多轮 agent 放在哪里（我的解读）

论文的叙事是多 agent 对单 agent。我觉得更干净的说法是：核开出的是一张账单，可以用两种货币来付。

单 agent 有一个容量 $W$，即一次执行里真正能用上的任务相关信息比特数；这是论文的第一条假设，也是人们一开始要拆任务的真实原因。如果核装不进 $W$，你有两条路。

第一条是拆。你用切割付账，$C_{\min}$ 比特，而且在封闭回路里这笔钱永远不退。

第二条是不拆，只用一个 agent 反复迭代：跑，拿反馈，再跑。这时你用反馈比特付账，每轮 $F$ 比特。每一轮最多买回反馈通道能承载的那么多比特。论文在 SWE-bench 上用测试结果的熵作为 $F$ 的代理，而一个通过/不通过的信号最多只有一比特。把相变线读成一个轮数预算：你需要的有效轮数至少是 $(c\,C_{\min} - H_{\mathrm{sol}})$ 除以每轮带回的比特数。预算不够，你就在图的红色一侧，再怎么调 prompt 也过不到绿色那边。更丰富的反馈（一段堆栈而不是一个红叉）会提高每轮的比特数、缩短预算。这就是为什么长程 agent 的生死取决于工具的质量，而不是上下文的长度。

这是解读，不是定理。论文没有显式建模轮数，真实 agent 每轮的反馈也不是一个干净的数字。但它解释了我反复看到的一件事：多 agent 系统失败的那些任务，恰恰也是单 agent 需要不合理多次迭代的任务。同一个核，两种货币。

碰到真实模型还成立吗

合成实验里的 agent 是按假设造出来的，真实 LLM agent 不是。所以论文在 SWE-bench Lite 上检验了四条方向性预测：46 个系统（18 个多 agent、18 个单 agent、10 个非 agent），300 个任务，约一万五千条结果记录。每个任务的 $C_{\min}$ 是这样估的：在真实补丁触碰的代码行上建依赖图，然后求精确的二分最小割。

四条方向都对，四条都显著。效应量不大，论文自己也这么说。三个原因，按让人心安的程度递减：定理是上界，真实系统可以远在上界之下；LLM agent 共享训练分布，可能存在隐式协调，这会削弱非冗余条件；还没有人在代码任务上验证过"无捷径"条件，而熟悉的代码模式确实可能让模型在没有约束信息的情况下直接猜出修法。把 SWE-bench 的数字当成"结构确实存在"的证据，而不是一个校准过的预测器。

我从中带走的东西

  • 先量核，再选架构。任务在低 $C_{\min}$ 处能拆开，agent 就是便宜的并行；拆不开，agent 就是一笔指数税。
  • 核大的时候去重构任务。加 agent 或者让它们多聊，都碰不到指数。
  • 预算要算反馈，不是算 token。能把一个 agent 系统推过相变的量，是每轮从世界拿回多少比特，以及你付得起多少轮。
  • 多 agent 和多轮是同一张账单的两种货币。选一种你的任务付得起汇率的。
